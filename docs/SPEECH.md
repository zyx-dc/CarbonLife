### 开场 [P1]（20s）

各位评委老师好。

我们的作品是 **CarbonLife 碳足迹**，一款基于 HarmonyOS 的低碳生活记录应用。

一句话说清它做什么：**把日常那些不起眼的低碳小动作，变成可记录、可量化、能坚持的东西。**⏸
走路去地铁站、少点一次外卖、把快递箱收好——这些事每个人都在做，但**没有一件被记下来过**。

### 问题 [P2]（35s）

我们把问题拆成三块。⏸

**难记录**：低碳行为太零散，没有统一入口，想记也不知道记在哪。
**没反馈**：一次绿色出行减了多少碳，没人告诉他，做了等于没做。
**难坚持**：没有激励、没有陪伴，好习惯撑不过一周。

还有一个现实问题：**用户对生活数据是有顾虑的**。所以我们一开始就划了一条边界——**数据默认留在本机，云备份是用户自己开的开关，默认关闭**。⏸
这条边界后面还会出现。

### 方案 [P3]（35s）

方案是一条很短的主线：**记录 → 计算 → 激励**。

▸[指向 P3 三个方块]

记一次行为，用**活动量乘排放因子**算出减排量，减排量折算成碳积分，积分再换成徽章、权益和一棵会长大的树。

关键是这三个数字**不是各算各的**：改一个源头，三个一起变。这一点决定了它不能靠点按钮刷出来。

### 用户 [P4]（20s）

三类人：**家庭用户**——一个人记容易懒，一家人一起记才持久；**学生**——把校园里的低碳实践变成看得见的东西；**通勤上班族**——每天固定通勤，最容易替换成低碳方式。

### 功能总览 [P5]（35s）

10 个功能覆盖完整闭环。挑三个说。⏸

**记录**：四大类、13 种行为，选行为、填数量，两步完成。
**看板**：日周月年四种周期，趋势看折线、结构看饼图，支持 CSV 和 JSON 导入导出。
**激励**：积分兑换、徽章、植树证书，加上这一轮做的**碳小树**和**碳账单**。

后面的时间我讲三个技术判断。

### 亮点 1 · 13 种行为怎么算 [P6]（30s）

每种行为对应一个排放因子：步行替代驾车每公里约 **0.17 千克**，地铁 **0.14**，公交 **0.12**。

▸[停顿]

工程取舍在这里：**因子表是一张独立的、可替换的表**。上层只关心"活动量 × 因子"，不关心数值本身。将来对接真实碳普惠平台，换表就行，业务代码不动。

### 亮点 2 · 端侧 AI [P7]（35s）

记录成本越低，人越愿意记。所以除了手选，还做了**拍照识别**。

▸[停顿]

用 HarmonyOS 的 **Core Vision Kit**，检测模型跑在设备上：识别出食物、车辆、植物、纸张，映射成最可能的低碳行为。注意是**推荐**不是自动记账——视觉识别有不确定性，自动写账会污染数据可信度。

**图片不出本机**，隐私和响应速度同时满足。真机上已跑通：相册选图 → 解码 1280×2800 → 检测出 36 个物体 → 命中「回收纸张」并自动选中。

### 亮点 3 · 看板与家庭 [P8]–[P9]（45s）

看板侧：四种周期、三种图表。导入是唯一的外部数据入口，所以做了两件事——**逐字段校验**（缺 id、日期非法、数值越界的记录直接丢弃），和 **RFC 4180 解析**（引号内的逗号、字段内换行、转义双引号都能正确拆）。简单逗号切分在这三种情况下都会错位，而真实 CSV 经常有这些。

家庭侧：用 **分布式数据对象**，同一华为账号的设备之间家庭码和数据自动合流，按成员展示各自的减排和积分，**不经过服务器**。

### 亮点 4 · 积分与碳小树 [P10]（60s）

▸[全场最该讲慢的一段，评委最可能追问]

积分能换权益、解锁徽章、拿植树证书——每减排 **10 千克**相当于种一棵树。

但真正想讲的是**碳小树怎么算**。⏸

第一条：**成长值完全由记录派生**。它是纯函数——输入是"每天几条记录、完成几个任务"，输出是成长值。没有"给树加 10 点"这种接口，所以前端点不出成长，也刷不了。

第二条：**每日上限 80**，而且上限作用在**连签加成之后的最终值**上。不封顶的话，最省力的那个行为会变成最优策略，激励就失真了。

第三条是我们讨论最久的：**断签不掉级**。断了只影响连续天数的展示，长出来的成长值不回收。因为掉级会制造焦虑——习惯类产品最大的流失点，就是用户断了三天后觉得"反正废了"，干脆不用。⏸
所以我们把坚持做成**正向奖励**（连续每天 +5%，封顶 +50%），而不是**惩罚中断**。

这套逻辑有 11 个单测锁着，包括"加成后仍然封顶"和"断档后连续归零"。

### 设计 [P11]（20s）

浅色和深色两套主题跟随系统，颜色、字号、圆角全部走设计 token；关键动效支持"减弱动效"开关。

### 技术底座 [P12]（40s）

四层：**入口层、五个页面、通用组件、数据服务层**。

- **ArkTS + ArkUI** 声明式 UI，Stage 模型，API 26。
- 存储：本机 **preferences**，记录序列化成 JSON。
- 状态同步：一个 **`recordsVersion` 计数器**——写入方自增，页面监听到变化后自己拉最新数据重算。没引入全局状态库，因为数据量小、页面少，全量重算完全够用。
- 端侧能力：Core Vision Kit 识图（真机已验证：36 个物体 → 命中回收纸张）、分布式数据对象做家庭（需双机）、后台代理提醒（受限权限，申请中）。
- 规模：**35 个 ArkTS 文件、约 6000 行**。

### 隐私 [P13]（20s）

三句话：**记录默认只在本机**；**云备份是可选开关，默认关闭**；**识图不出本机，家庭同步不经第三方**。

这不是口号，是架构选择——所有核心功能都不依赖网络。

### 质量 [P14]（20s）

怎么保证它不是"能编译"而是"能用"？四道门禁：**构建通过、静态检查 0 error、单测 21 项全过、UI 冒烟 20 项全过**，再按清单在设备上逐条对照预期。

▸[停顿]

冒烟脚本抓出过一次真回归：加滚动提示时用了全屏浮层，结果吞掉滚动手势，页面滑不动——这种问题单元测试永远发现不了。

### 展望 [P15]（15s）

下一步三件事：**接真实碳普惠平台**、**完成云备份的多设备冲突合并与真机验证**、**补无障碍和平板布局**。不再加新玩法，先把这三件做实。

▸[收]

低碳不是打卡任务，是一种能长期过下去的生活方式。谢谢各位老师。

```
├─────────────────────────────────────────────────────────┤

│  组件层  AppCard  AppButton  TaskCard  Badge              │

│          图表：折线 / 柱状 / 饼图（自绘）                  │
├─────────────────────────────────────────────────────────┤
│  服务层  CarbonStore（数据 + 导入导出 + 版本号）           │
│          CarbonFactors（因子表）   Sapling（成长算法）     │
│          Rewards / MallService（积分与兑换）               │
│          VisionService（端侧识图）                         │
│          FamilyService（分布式数据对象）                   │
│          ReminderService（后台提醒）                       │
│          BackupService / CloudAuth / CloudBackup（备份）   │
└─────────────────────────────────────────────────────────┘
```

**一句话版本**（评委问"你们怎么分层"）：

> 「上层只管渲染，下层只管数据和规则。页面不直接算减排，只调 `CarbonStore`；算法不碰 UI，`Sapling` 是纯函数，所以能单测。」

### 2.2 一条记录的完整链路（最该背熟的一条）

```
用户点"保存记录"
      ↓
RecordTab 拿到 behaviorKey + 数量
      ↓
CarbonFactors.find(key) → 取因子（如 0.17 kg/km）
      ↓
saved = amount × factor；points = saved × 100（取整）
      ↓
CarbonStore.addRecord() → 写入 preferences（JSON）
      ↓
versionCounter++  →  AppStorage['recordsVersion']
      ↓
各页面 @StorageLink 监听到变化 → 各自重新计算
      ↓
首页：今日减排 / 积分 / 成长值同时变
看板：趋势与构成重算
小树：Sapling.compute() 用「每天记录数」重算成长值
```

**为什么用版本号而不是状态库**：
> 「数据量小、页面少，只需要一个『数据变了』的信号。页面自己拉最新数据重算，避免多处持有副本导致不一致。代价是全量重算，几千条记录完全扛得住。」

### 2.3 成长算法（必须能手推）

```
每天原始成长 = 记录条数 × 10 + 完成任务数 × 15
连签加成     = min(50%, (连续天数 − 1) × 5%)
当天成长     = min(80, round(原始 × (1 + 加成)))     ← 上限作用在最终值
累计成长     = 各天相加（断签不回收）
阶段         = 0 / 60 / 180 / 420 / 900 / 2400 → 种子/幼苗/小树/开花/结果/常青
```

**举现场例子（背熟这个）**：
> 「种子数据是 5 天、每天 4 条，所以每天 40 点，连签加成第 5 天是 20%，合计 220 点，正好是小树。今天我记 1 条并完成两个任务，原始 10+30=40，第 6 天加成 25%，得 50 点，累计 270，连续 6 天。」

### 2.4 四个"为什么"（评委会挑的地方）

| 追问 | 答法（先给结论，再给理由） |
|---|---|
| 为什么上限是 80？ | 80 大约等于 5–8 条有效记录，正好覆盖真实的一天；再往上就不是记录，是刷数。 |
| 为什么断签不掉级？ | 掉级制造焦虑，断三天就弃用，这是习惯产品的头号流失点。我们只惩罚"今天的加成"，不没收历史。 |
| 为什么不用状态管理库？ | 数据量小、页面少，一个版本号足够；引入库的收益小于维护成本。 |
| 为什么因子是硬编码表？ | 它本质是**可替换的字典**。接真实平台时换表，不动业务代码——这是分层的目的。 |

## 三、技术追问：8 个必须能答的

> 每题先背"短答"（15 秒），再看"底层"（被追时才展开）。

**Q1 你的成长值到底怎么防刷？**
短答：它是纯函数，输入只有"每天几条记录、几个任务"，没有可写的成长值字段，前端点不出来。
底层：`Sapling.compute()` 只读 `records` 和 `taskRewards`，按天聚合后累加，上限作用在连签加成之后的最终值上。改代码才能改成长，改数据只能改记录——而记录有导入校验。

**Q2 断签不掉级，那用户断一年回来还是小树，合理吗？**
短答：合理，因为成长值代表"你曾经做过多少"，不代表"你现在有多活跃"。活跃度用连续天数表达。
底层：`lastActiveTs` 与今天的差值 > 1 天时只把 `streak` 置零，`growth` 不动；`bestStreak` 也保留。这是产品决策，写在代码注释里。

**Q3 端侧 AI 识别不准怎么办？**
短答：不当自动记账用，只做推荐，用户确认才写入；置信度低于 0.45 直接丢弃；识别失败回落手动选择。
底层：`VisionService.pickAndDetect()` 走 `photoAccessHelper` → `ImageSource` → `PixelMap` → `ObjectDetector.process()`，标签映射表集中维护，加场景只加一行；`finally` 里统一释放检测器、像素图、图片源和文件句柄。

**Q4 家庭是怎么同步的？没有服务器？**
短答：用 HarmonyOS 的**分布式数据对象**，同一华为账号的设备间自动合流，不经过我们的服务器。
底层：`FamilyService` 用 `distributedDataObject.create(ctx, model)`，家庭码做房间标识；每台设备写自己的成员条目。**前提是两台同账号设备**，单机验证不了，我们如实标了"待双机"。

**Q5 云备份、提醒、识图，为什么真机上用不了？**
短答（一次说清三件，别分开挤牙膏）：三个都在验收表里标了未通过，原因各不相同——
**云备份**：AGC 云存储桶在当前应用身份下取不到，模拟器和真机都返回 403，判断是 AGC 侧开通与绑定没完成，不是业务代码问题；本地备份、导出、导入都正常。
**提醒**：`PUBLISH_AGENT_REMINDER` 是受限权限，需要华为侧 ACL 授权，当前调试签名没有这份 profile，发布提醒会被拒。
**识图**：图片选择器在真机上没能拉起，还没拿到设备日志，端到端没验证，所以只标"入口可用"。
底层（被追时才展开）：AGC 匿名登录和建桶都成功，卡在 `GetDefaultBucket`；排查过权限、签名、调试凭据注册、安全规则、应用身份（appIdentifier 和 AGC 的 APP ID 是两套编号）。提醒的权限我们只声明了 name/reason/usedScene，缺 `acls` 声明——但要真正生效还需要带该权限的签名 profile，这不是改代码能解决的。**验收文档里连没过关的都单列了状态，没有把未验证写成通过。**

**Q6 导入为什么值得单独做校验？**
短答：导入是唯一的外部入口，一条坏数据能让整个列表渲染崩掉，所以宁可丢也不让它进来。
底层：两件事——结构校验（必须数组、必须有 id、日期可解析）+ 归一化（缺省补默认、数值收敛）。CSV 手写 RFC 4180 扫描器，处理引号内逗号、字段内换行、`""` 转义；导出加 BOM 让 Excel 不乱码。

**Q7 你们怎么证明它真能跑，而不只是能编译？**
短答：四道门禁 + 设备逐条验收。构建、静态检查 0 error、单测 21/21、UI 冒烟 20/20，再按清单在设备上对照预期。
底层：冒烟脚本会真的点每个 Tab、dump 布局树、断言导航还在，所以能抓到单元测试抓不到的交互回归——比如全屏浮层吞掉滚动手势那次。

**Q8 这个项目 AI 占多少？**
短答：辅助环节。架构、数据模型、成长算法、同步机制我们先设计，AI 帮我们写和查，我们逐条改、逐条验。
底层（拿证据）：
- 成长算法的三条取舍（上限 80、加成后仍封顶、断签不掉级）是产品判断，写在 `Sapling.ets` 注释里，11 个单测锁行为；
- 状态同步选 `recordsVersion` 而不是状态库，是权衡数据量和页面数；
- 导入校验的字段清单和 RFC 4180 的三种边界，是拿真实坏数据调出来的；
- 验收文档里连"没验证过的"都单独标了状态（云备份 BLOCKED、家庭待双机）。
