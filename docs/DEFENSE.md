## 0. 一句话定位（开场 15 秒，背下来）

> 「CarbonLife 是一款 HarmonyOS 原生的低碳生活记录应用。它做三件事：**把日常低碳行为变成可量化的减排量，把减排量变成可持续的激励，把数据留在用户自己的设备上。**」

三个关键词，全场反复回扣：**可量化 / 可持续 / 隐私优先**。

## 2. 现场演示脚本（3.5 分钟，5 个动作）

> 目标：让评委在 3.5 分钟内看到 **记录 → 计算 → 反馈 → 沉淀 → 分享** 的完整闭环。
> 每个动作只说 1–2 句，**手比嘴快**：点完再讲。

### 动作 1 · 首页（40 秒）

**点**：无（停在首页）

**讲**：
> 首页是「一屏结论」：今天减排多少、多少积分、累计减排、相当于种了几棵树。下面是今天的三条主线——每日任务、碳小树、最近记录。
> 注意这个数字：**今日减排 0.00 kg**，等一下我记一条，它会当场变。

**指**：顶部四个数字 → 碳小树卡片（此刻已有种子数据：小树 / 220 / 连续 5 天 / 偏向绿色出行）

### 动作 2 · 记录一条（60 秒，全场核心）

**点**：底部「记录」→ 类别「出行」→ 行为「步行替代驾车」→ 数量用 `+` 加到 3 km → 「保存记录」

**讲**：
> 13 种行为分四类：出行、节能、回收、餐饮。每种行为背后是一个排放因子——步行替代驾车按公里折算，节约用电按度折算。
> 这里我特意做了 `−/+` 步进器：数量必须能**精确设定**，不能只有一个凭手感的滑杆。
> 保存。

**预期**：Toast「记录成功」→ 自动回首页 → **今日减排、积分、成长值同时跳变** → 每日任务「绿色出行」「坚持记录」自动打勾。

**讲（关键句，务必说）**：
> 这三个数字不是各算各的：**减排量由「活动量 × 排放因子」算出，积分由减排量折算，成长值由记录条数派生**。改一个源头，三者一致变化。这就是为什么它不能靠点按钮刷。

### 动作 3 · 碳小树 + 碳账单（60 秒，差异化亮点）

**点**：首页「碳小树」卡片（整卡可点，等同「生成成果卡片」按钮）→ 直接打开碳账单

**讲**：
> 碳小树把抽象的减排沉淀成一棵**会长大的树**：种子、幼苗、小树、开花、结果、常青六个阶段，阈值 0 / 60 / 180 / 420 / 900 / 2400。
> 三条防刷设计：**成长值完全由记录派生**（没有可写状态）；**每日上限 80**，连签加成也不能突破；**断签不掉级**——只影响连续天数展示，成长值不回收。
> 连续记录每天加 5%，封顶 50%。这是"奖励坚持"，不是"惩罚中断"。

**指碳账单**：
> 这张账单是一页结论：树的阶段与偏向、累计减排、积分、种树数、活跃天数、最长连续，下面是**减排构成**——哪一类贡献最多一眼看到。
> 可以复制文案，也可以**保存成图片**（端侧截图 → PNG → 系统文件选择器，不申请额外权限）。

**点**：「复制文案」→ 展示粘贴结果（可选）

### 动作 4 · 看板（40 秒）

**点**：底部「看板」→ 切「周」→ 再切「月」

**讲**：
> 日 / 周 / 月 / 年四种周期，折线看趋势、柱状看对比、饼图看结构。
> 数据支持 CSV 和 JSON 导入导出。导入我做了两件事：**逐字段校验**（缺 id、日期非法、数值越界的记录直接丢弃）和 **RFC 4180 解析**（带引号的逗号、换行、转义双引号都能正确拆）。坏文件不会污染本机数据。

### 动作 5 · 积分 + 科普 + 深色（30 秒，快速掠过）

**点**：底部「积分」→ 底部「科普」→（可选）下拉控制中心切深色

**讲**：
> 积分可以兑换权益、解锁徽章和植树证书；商城会标出「最接近可兑换」的一项。
> 科普是 6 篇双碳专栏加一个 5 题自测。
> 全站浅深双主题跟随系统，所有文案走资源键，中英双语。

### 收尾（15 秒）

> 这套东西的技术底座是 HarmonyOS 原生的：ArkTS + ArkUI 声明式 UI、Stage 模型、本机 preferences 存储、端侧 AI 识图、分布式数据对象做家庭聚合。
> **记录默认只在本机，云备份是用户自己开的开关，默认关闭。** 这是我们做这个产品最先定下的边界。

## 4. Q&A（16 题，按被问概率排序）

> 每题给**短答（15 秒）**和**深答（40 秒，被追问时用）**。短答背熟，深答理解即可。

### 4.1 核心算法（最可能被问）

**Q1. 碳小树的成长值怎么算？会不会被刷？**

- 短答：成长值完全由记录派生，没有独立的可写状态。每天 = `min(80, 记录数×10 + 完成任务数×15)`，再乘连续加成（每天 +5%，封顶 +50%），**加成后的最终值仍然封顶 80**。
- 深答：因为它是**纯函数**——输入是"每天有几条记录、完成几个任务"，输出是成长值。没有"给树加 10 点"这种接口，所以前端点不出成长。上限作用在最终值上，是为了防止"连签加成把上限顶掉"。这套逻辑有 11 个单测覆盖，包括"加成后仍封顶"和"断档后连续归零"。

**Q2. 为什么每日上限是 80？**

- 短答：80 约等于 5–8 条有效记录，正好覆盖一天真实的低碳行为；再往上就不是记录，是刷数。
- 深答：如果不封顶，最省力的行为（比如反复记"光盘行动"）会变成最优策略，激励就失真了。80 是让"正常一天"能走完、让"刷一天"没有额外收益的平衡点。阶段阈值 60 / 180 / 420 也是按这个节奏设计的——**幼苗约 1 天，小树约 3 天，开花约 6 天**。

**Q3. 连续记录加成怎么算？断签了会怎样？**

- 短答：连续第 N 天加成 `min(50%, (N−1)×5%)`。**断签不掉级**：成长值不回收，只有"连续天数"展示归零，卡片会显示「上次连续 N 天」。
- 深答：这是产品决策。掉级会制造焦虑，用户一旦断了就会放弃整个应用——这是习惯类产品最常见的流失点。所以我们把"坚持"做成正向奖励，"中断"只影响当天加成，历史成果全部保留。连续天数只在**相邻自然日**累加，中间断档从 1 重新开始。

**Q4. 排放因子是哪来的？准不准？**

- 短答：用的是公开的低碳行为减排参考值，按"活动量 × 因子"折算成 kg CO₂e，**定位是量级正确的估算，不是碳核查**。
- 深答：我们不在答辩里声称"精确计量"。产品定位是**行为激励**：同一行为不同人、不同地区会有差异，因子表是集中在 `CarbonFactors.ets` 里的一张可替换表，后续接真实碳普惠平台时替换这一层即可，上层逻辑不变。这是有意做的分层。

### 4.2 架构与实现

**Q5. 数据存在哪？状态怎么同步到各个页面？**

- 短答：本机 `preferences`，JSON 序列化。页面之间用一个 `recordsVersion` 计数器做失效通知——写入方自增，各页面 `@StorageLink` 监听后重算。
- 深答：没有引入全局状态库，因为数据量小、页面少。`recordsVersion` 只承担"数据变了"这一个信号，页面自己从 `CarbonStore` 拉最新数据重算，避免多处持有副本导致不一致。这个取舍的代价是全量重算，在几千条记录的量级上完全可以接受。

**Q6. 导入为什么需要"校验归一化"？**

- 短答：导入是唯一的外部数据入口。缺 id、日期非法、数值越界、非 JSON 的记录会被丢弃，而不是让一条坏数据把整个列表渲染崩掉。
- 深答：两件事。一是**结构校验**（必须是对象数组、必须有 id、日期能被解析）；二是**归一化**（缺省字段补默认值、数值收敛到合法区间）。CSV 那边我手写了 RFC 4180 解析，处理带引号的逗号、字段内换行、转义双引号——因为简单的 `split(',')` 在这三种情况下都会错位，而现实里的 CSV 经常有这些。

**Q7. 端侧 AI 是怎么做的？**

- 短答：调用 HarmonyOS 的端侧图像识别能力，对用户选定的照片做物体分类，把结果映射到 13 种行为里最接近的一种，作为推荐。**图片不上传**。
- 深答：这里我们做的是"推荐"不是"自动记账"——识别结果是候选，用户确认后才生成记录。原因是视觉识别有不确定性，自动写账会污染数据可信度。端侧推理同时满足隐私和响应速度两个目标。

**Q8. 家庭碳积分怎么实现的？为什么演示不了？**

- 短答：用分布式数据对象（DDO）在同一华为账号的设备间同步家庭码和记录摘要，按成员聚合。
- 深答：它的前提是**两台登录同一账号的设备**，模拟器上没法构造第二台，所以这项我们只验证了本地侧聚合逻辑，跨设备同步标注为"待双机验证"。我们在验收文档里如实标了状态，没有把它算成 PASS。这是刻意的——**没验证过的不写成通过**。

### 4.3 风险与边界（最容易被追问）

**Q9. 云备份为什么标成 BLOCKED？**

- 短答：模拟器上 `GetDefaultBucket` 恒返回 403，即使把安全规则放开到 `if true` 仍然 403，所以判断不是规则或权限问题，而是模拟器侧凭据/环境限制。需要真机或提工单。
- 深答：排查过的方向包括：权限声明、签名、模拟器调试凭据注册（已注册成功）、安全规则（回滚为 `request.auth.uid != null` 之后仍是 403）、应用身份（appIdentifier 和 AGC 的 APP ID 是两套编号）。匿名登录和建桶都成功，卡在取默认桶这一步。**本地备份、导出、导入不受影响**，功能可用性没有打折。我们没有为了"看起来能跑"而伪造成功。

**Q10. 你们用了 AI 多少？哪些是 AI 写的？**

> **这题必须答得稳。评审原则写明：讲不清核心逻辑会被复核，过度依赖 AI 直接取消资格。**

- 短答：AI 用在**代码提示、文案润色、UI 素材和调试辅助**这些非核心环节；业务架构、数据模型、成长算法、状态同步是团队设计并逐条验证的。核心逻辑我可以现在就打开代码讲。
- 深答（被追问时给具体证据）：
  - **数据模型**（记录 / 任务奖励 / 兑换 / 徽章 / 家庭）是我们先画出来再写的；
  - **成长算法**的取舍——每日上限 80、加成作用在最终值、断签不掉级——是产品决策，写在 `Sapling.ets` 的注释里，有 11 个单测锁行为；
  - **状态同步**用 `recordsVersion` 而不是状态库，是权衡数据量和页面数后的选择；
  - **导入校验**的字段清单和 RFC 4180 的三种边界情况，是我们对着真实坏数据调的；
  - 我们跑 **21 个单测 + 20 项 UI 冒烟 + 逐条设备验收**，验收文档里连"没验证过的"都单独标了状态。
- **兜底句**：「如果评委想核验，我可以打开任意一个模块，从数据结构讲到边界条件。」

**Q11. 这个和市面上的碳积分小程序有什么区别？**

- 短答：三件事。**端侧 AI 降低记录成本**、**碳小树把减排沉淀成长期可见的成长**、**数据默认本机 + 家庭聚合**。
- 深答：小程序类产品通常是"记一笔给积分"，缺少长期反馈，也缺少家庭维度。我们把"记录"和"沉淀"分开：记录是即时的，碳小树和碳账单是长期的。而且我们不做排行榜式的社交攀比——那会诱导刷数，和"真实减排"的目标相反。

**Q12. 如果没有网络 / 没有云，还能用吗？**

- 短答：能，而且这是默认状态。记录、计算、图表、碳账单、导入导出全部本地完成；云备份是可选开关，默认关闭。
- 深答：这是架构上的选择而不是降级方案。所有核心功能不依赖网络，网络只用于可选的云备份。代价是跨设备同步需要用户主动开云备份或走家庭分布式，我们接受这个代价。

### 4.4 工程与质量

**Q13. 你们怎么保证它"能用"而不是"能编译"？**

- 短答：四道门禁 + 设备逐条验收。构建通过、lint 0 error、单测 21/21、UI 冒烟 20/20，再按验收清单在模拟器上逐项对照预期。
- 深答：静态检查抓不住交互问题，所以冒烟脚本会真的点每一个 Tab、dump 布局树、断言导航还在。这套脚本还抓出过一次真实回归：我加滚动提示时用了全屏浮层，结果**吞掉了滚动手势**，页面滑不动——是冒烟 + 手动复现一起发现的，改成内容流内提示才修好。这类问题是单元测试永远发现不了的。

**Q14. 单测覆盖了什么？**

- 短答：21 个，集中在**纯逻辑**：日期工具、排放因子查找、导入校验、成长算法。
- 深答：成长算法占 11 个，覆盖阈值边界、单日封顶、加成后仍封顶、任务计数、连续加成、断档归零、满级。选这些是因为它们是**最容易悄悄错、错了又看不出来**的地方——UI 上数字差 10 没人会发现，但算法错了整个产品的可信度就没了。

### 4.5 产品与规划

**Q15. 下一步做什么？**

- 短答：三件——对接真实碳普惠平台 API、完成云备份的冲突合并与真机验证、补无障碍与平板多列布局。
- 深答：优先级是"可信度"优先于"功能数"。因子表接真实平台数据是可信度的根；云备份要解决的是多设备写入冲突（现在只有整包快照，没有合并策略）；无障碍和平板布局是可用性债务。我们不打算再加新玩法，先把这三件做实。

**Q16. 为什么叫 CarbonLife？**

- 短答：碳（Carbon）+ 生活（Life）。我们想表达的是"低碳不是任务清单，是一种生活方式"，所以核心隐喻是一棵会生长的树，而不是一个积分账户。
